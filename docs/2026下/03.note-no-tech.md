## 台账是啥

`2026-09-26`



## 台账 = 「要跟进事项的活档案」

字面来源：传统商铺放在**台**面上的**账**簿（台 + 账），即明细登记本。

延伸到工程管理领域后，它特指：**针对某一类事物逐条登记、持续维护状态、责任到人的明细记录**。

### 三个核心特征

| 特征 | 说明 |
|---|---|
| **逐条登记** | 每条对应**一个对象**（一个缺陷、一台设备、一个隐患），不是一次事件 |
| **状态流转** | 待处理 → 处理中 → 已关闭，状态会被人改 |
| **责任到人** | 有 owner、有处理时限、可追溯 |

---

## 跟"日志""报表"的区别（容易混）

| | 记什么 | 能改吗 | 回答什么问题 |
|---|---|---|---|
| **日志**（log / traces） | 事件流水 | 只追加，不改 | "发生了什么" |
| **报表**（report / stats） | 统计汇总 | 每次重算 | "有多少、趋势如何" |
| **台账**（ledger） | **对象 + 状态** | **人会改** | "这事归谁、跟到哪一步了" |

**一句话类比**：
- 日志 = 每天花了什么钱的流水
- 报表 = 这个月总共花了多少
- **台账 = 家里有几件待修的东西、谁负责修、修到哪一步了、修好没有**

---

## 在你刚看的飞轮项目里，"台账"具体指什么

`badcase_problems` 表就是**缺陷台账**，每条 = 一个归并后的根因：

```
一条台账记录：
  merged_root_cause = "工具参数/Schema 不匹配"   ← 缺陷身份（对象）
  channel           = 表格                        ← 归属品类
  owner             = 张三                        ← 责任到人
  status            = 处理中                      ← 状态流转
  tapd_id           = 123456                      ← 关联单据
  first_seen / last_seen = 首次/末次出现
  impact_count      = 影响会话数
```

对比一下就清楚了：
- `sessions` / `traces` = **流水**（每次会话的记录）
- `stats_daily` = **报表**（每天的统计数字）
- `badcase_problems` = **台账**（这类问题归谁、跟到哪一步了）

### 为什么这个设计是对的（值得留意）

代码里有个关键约束：`badcase_problems` **不带 source、不带 period**，唯一键是 `(channel, merged_root_cause)`，**时间窗只在读端切片**。

意思是：**台账里存的是"缺陷身份"本身，不按天、不按数据源重复建条目**。

因为——同一个错误码在 langfuse/wedata 上是同一个平台问题，跨了两周也还是同一个。如果按天建台账，一次故障就会被记成 N 个缺陷，owner 和状态会被冲散，台账就退化成流水了。

还有个细节很关键：**机器列和人工列严格分离**——自动聚合只更新机器列（影响数、首末日），`owner`/`status`/`tapd_id` 这些人工列不会被下一轮聚合覆盖。否则你今天填的负责人，明天就被程序刷没了，台账也就没人愿意维护了。

---

项目里叫"台账"的还有几处，都是同一个意思：
- `RootBattlePanel` → **根因治理台账**（按根因跟进治理进展）
- `RejudgeRecordsPage` → **人工改判台账**（谁改判了哪条评分）
- `badcase_problem_tickets` → 建单记录

## sheet的质量门禁是profile规定的吗，超过多少是不通过呢

`2026-09-26`

这个问题有两层（评测及格线 vs CI 发布门禁），我分开查。
## 结论：不是 Profile 规定的 —— 门禁有自己独立、且更严的一套线

这里有两层，很多人会混：

| | 谁规定 | 在哪 | 回答什么问题 |
|---|---|---|---|
| **评测及格线** | Profile | `profiles/sheet_*.yaml` 的 `overall_threshold: 65.0` | 这个 case 做得**好不好** |
| **发布门禁红线** | 门禁脚本 + 选集配置 | `scripts/release_gate.py` + `configs/gate_selection/sheet.yaml` | 这批 case 跑完**能不能发版** |

**关键：门禁故意不读 Profile/suite 的 `passed` 字段。** 代码注释写得很直白：

```133:138:scripts/release_gate.py
分数量纲（易踩坑）:
  上游 overall_score 是 0~1 归一化值（如 0.57342），suite 默认 pass 线 0.5
  （summary.json 的 pass_criteria.threshold）。门禁用更严的 0.65，且**不读上游
  passed 字段**——读它等于用 0.5 线放水。旧版 CASE_PASS_THRESHOLD=65.0 与 0~1
  量纲不匹配（永远为 False），靠上游 passed 兜住才没暴露。
```

> 顺带一个真实的历史坑：早期 `CASE_PASS_THRESHOLD = 65.0` 但分数是 0~1 量纲 → `score >= 65.0` **永远为 False** → 门禁其实一直没生效，全靠上游 `passed` 兜着。现在统一成 0~1 的 `0.65` 才真正拦得住。

---

## 门禁的阈值（`scripts/release_gate.py:294-302`）

```python
CASE_PASS_THRESHOLD = 0.65   # 单 case 及格线（0~1）
L2_PASS_RATE_MIN    = 0.80   # L2 动态集通过率下限
ERROR_RATE_MAX      = 0.15   # 执行错误率上限
```

## 六条红线（G0~G4）

| 规则 | 条件 | 判什么 |
|---|---|---|
| **G0** L0 冒烟 3 个全过 | 有执行错误 → **INVALID**；无错但打分挂 → **FAIL** | 链路活性 |
| **G1** L1 核心集 | 有任何失败 → **FAIL** | 主流程（零容忍） |
| **G1k** L1 稳定性 | `pass^k` < 0.5 → **FAIL**（`block=true` 时；灰度期仅 WARN） | 反复用会不会时灵时不灵 |
| **G2** L2 动态集 | 通过率 < **80%** → **FAIL** | 本次改动 |
| **G3** 相对 baseline | pass→fail 回归 → **FAIL**；均分跌 > 8 分 → 默认 WARN | 有没有退化 |
| **G4** 错误率 | > **15%** → **INVALID** | 结果可不可信 |

**判定顺序很讲究：先判 INVALID（G0-error / G4），再判 FAIL。** 理由是"高错误率下 FAIL 的结论本身就不可信，不该拿去拦人"——环境问题不该让开发背锅。

三种结论：`PASS`(退出码 0) / `FAIL`(1) / `INVALID`(2)。

## 分层与数量（`configs/gate_selection/sheet.yaml`）

| 层 | 定位 | 数量 | 行为 |
|---|---|---|---|
| **L0 冒烟** | 打开文档→唤起 Agent→产出文件→评分器能跑 | **3**（每条链路各 1） | 挂则 fail-fast |
| **L1 核心集** | 主流程，与本次改动无关也永远不能坏 | **≤16** | retry 1 次仍挂 → FAIL |
| **L2 动态集** | 本次改动命中的能力 | **≤8** | 通过率 <80% → FAIL |

准入有个硬规约值得注意：**L0/L1 的 case 必须有产物硬校验**（`hard_checklist_keys: [sheet_audit, contains]`）—— 注释说得很准："只有 content_judge 的 case 等于让 LLM 看 Agent 自述打分，弱信号高噪声"。

1. **在哪**：`configs/gate_selection/sheet.yaml`（分层名单+范围，**人工维护唯一入口**）+ `scripts/release_gate.py`（阈值常量+判定逻辑，产品无关）

## 墙钟时间

`2026-09-26`

## 墙钟 = 现实世界真实流逝的时间

英文 **wall-clock time**（墙上挂钟走过的时间）。就是你抬头看表、看手机，从 `14:00:00` 到 `14:05:00` 这**真实过去了 5 分钟**——不管这期间你的程序是在疯狂计算、还是在发呆 sleep、还是在等锁。

它专门用来和另外两种"时间"区分开：

| 概念 | 含义 | 例子 |
|---|---|---|
| **墙钟时间** | 现实流逝的秒数 | 程序 sleep(10)，墙钟过了 10 秒 |
| **CPU 时间** | CPU 真正干活的时间 | 同上，CPU 时间≈0（进程在睡） |
| **迭代次数/轮次** | 逻辑计数，不是时间 | 轮询了 280 次 |

---

## 回到刚才那个 bug：为什么"轮次"会骗人

原来的停滞判死逻辑长这样（伪代码）：

```
轮询计数 = 0
while 还没完成:
    检查一次()
    轮询计数 += 1
    if 轮询计数 > 280:   # 以为 280 × 3s ≈ 14 分钟
        判死()
```

**隐含假设：每次轮询耗时恒定 3 秒。** 写代码的人按这个假设算出预算 ≈14 分钟。

但真实情况是：因为**锁竞争**（那个 `_ui_lock` 被别的任务占着），每次轮询实际要等 25 秒。于是：

- 你以为：280 轮 × 3s = **14 分钟**判死
- 实际：280 轮 × 25s = **39 分钟**才判死

而整个任务的墙钟超时可能只有 20 分钟——结果就是**守卫的判死条件永远达不到**，要么进程先被外层墙钟超时干掉，要么硬生生拖到 39 分钟。

**改成墙钟之后**：

```
开始时间戳 = now()
while 还没完成:
    检查一次()
    if now() - 开始时间戳 > 300秒:   # 产物档 300s / 非产物档 180s
        判死()
```

现在**不管单次轮询被拖多慢**（3s 也好、25s 也好），判死时机都是确定的 300 秒。单次迭代变慢不再放大总预算。

---

## 一句话记住

**"数到 280 下就停" vs "看表，过 5 分钟就停"** —— 前者在你数得慢的时候会失控，后者永远准。

所以工程上有条经验：**超时/判死这类兜底，一律用墙钟时间，不要用迭代次数。** 用次数做超时，等于偷偷假设了"每次迭代耗时恒定"，而这个假设在并发、锁竞争、网络抖动下几乎必然不成立。

（同理，日志里常见的 `duration`、`elapsed_ms`、以及 `time.time()` 打点算出来的，都是墙钟；而 `time.process_time()` 才是 CPU 时间。）

## Vue3 [Boolean String] Props

`2026-09-03`

静态无冒号属性：

1. `[Boolean, String]`（Boolean 在前，开启布尔规则）：**只要写了属性（`disabled` / `disabled=""`），一律解析为`true`**
2. `[String, Boolean]`（String 在前，关闭布尔规则）：**写`disabled=""`得到空字符串`""`，写`disabled`也得到`""`**

>
> 仅限不带`:`静态 attribute；`:value`动态绑定不受这套规则。

### 对照文档 4 种情况：

- `<MyComponent disabled />` + `[Boolean, String]` → `true`
- `<MyComponent disabled="" />` + `[Boolean, String]` → `true`
- `<MyComponent disabled />` + `[String, Boolean]` → `""`
- `<MyComponent disabled="" />` + `[String, Boolean]` → `""`

## 服务器启动 rabbitmq

`2026-09-03`

逐行解析这条 RabbitMQ 的 docker run 命令

```bash
docker run -d --name rabbitmq \
  -p 127.0.0.1:5672:5672 \
  -p 127.0.0.1:15672:15672 \
  --restart unless-stopped \
  -e RABBITMQ_DEFAULT_USER=blog \
  -e RABBITMQ_DEFAULT_PASS=xxx \
  rabbitmq:3.13-alpine
```

> `\` 只是**换行续行符**，作用是把一条长命令拆成多行方便阅读，没有实际功能。

---
1. **`docker run`**
核心命令：创建并启动一个新的docker容器。

2. **`-d`**
全称 `--detach`，**后台守护进程运行**。
容器启动后放到后台，不会占用当前ssh终端窗口；不加 `-d` 会直接把rabbitmq日志输出在前台，关掉ssh窗口容器就停止。

3. **`--name rabbitmq`**
给这个容器起名字叫 `rabbitmq`。
后续操作可以直接用名字，不用容器ID：`docker stop rabbitmq` / `docker logs rabbitmq`。

4. **`-p 127.0.0.1:5672:5672`**
端口映射，格式：`宿主机地址:宿主机端口:容器内端口`
- 容器内部rabbitmqAMQP协议端口是`5672`（业务程序收发消息用）
- `127.0.0.1` = **宿主机回环地址**
✅ 含义：**只允许这台服务器本机内部程序访问5672端口，外网其他机器完全连不上**（正好是你想要的，禁止公网访问）

5. **`-p 127.0.0.1:15672:15672`**
同样端口映射：
- `15672` 是 RabbitMQ Web管理后台端口
- 同样绑定`127.0.0.1`，**只能在这台服务器内部浏览器/curl访问web后台，外部无法访问**

> 端口映射规则小结：`-p 宿主机IP:宿主机端口:容器端口`
> 如果写 `-p 5672:5672`（不写127.0.0.1），会绑定到服务器所有网卡，公网就能访问。

6. **`--restart unless-stopped`**
容器重启策略：
- 只要不是**手动执行docker stop**把容器关掉，其他情况自动重启
  - 服务器重启 → 容器自动启动
  - rabbitmq进程崩溃异常退出 → 自动重启
- 对比：
  - `always`：就算手动stop，宿主机重启也会起来
  - `unless-stopped`：最适合生产，推荐

7. **`-e RABBITMQ_DEFAULT_USER=blog`**
`-e` = `--env` 设置环境变量。
RabbitMQ启动时自动创建**默认管理员账号**，用户名：`blog`
> 镜像自带的环境变量，容器第一次启动生效，容器建好之后再改这个环境变量没用。

8. **`-e RABBITMQ_DEFAULT_PASS=xxx`**
配套环境变量，设置上面`blog`账号的密码。

9. **`rabbitmq:3.13-alpine`**
指定使用的镜像：
- `rabbitmq`：镜像名
- `3.13`：rabbitmq版本号
- `alpine`：基于alpine极简Linux，镜像体积小

> ⚠️注意：`rabbitmq:3.13-alpine`镜像**默认不带web管理插件**，容器启动成功后，你需要手动进容器执行：
> ```bash
> docker exec -it rabbitmq sh
> rabbitmq-plugins enable rabbitmq_management
> ```
> 启用web后台，否则`15672`网页打不开。


## Redis 设置密码和连接

`2026-09-03`

1. **设置密码**
- 临时命令（重启失效）：`CONFIG SET requirepass "密码"`；`CONFIG REWRITE`写入配置持久化
- 永久配置：编辑 `/etc/redis.conf`，取消注释 `requirepass 你的密码`，重启redis生效

2. **客户端连接**
- `redis-cli`：每次执行都**新建独立连接**；进入交互终端可连续执行多条Redis命令
- `redis-cli -a mypassword`：连接时直接带密码（长参数`--auth`；⚠️密码会暴露在进程列表，生产不推荐）
- 安全写法：`redis-cli` 连上后，再执行 `AUTH mypassword` 认证

3. **后台启动**
`redis-server --daemonize yes`：以守护进程后台启动，**Mac、Linux都支持，Windows不支持**；仅本次启动生效，不修改配置文件。
> 优雅停止：`redis-cli shutdown`

4. 补充：Linux生产一般用`systemctl start redis`托管；Mac brew可`brew services start redis`

### 制品类型（重点解释）

`OCI-Image-v1`

#### 1) OCI 是什么
**OCI = Open Container Initiative（开放容器规范）**
是 Docker、containerd、K8s 共同遵守的国际容器标准，由 Linux 基金会维护。

#### 2) OCI-Image-v1 含义
- `OCI-Image`：代表这是符合 OCI 标准的容器镜像，不是 Docker 私有的老式格式；
- `v1`：OCI 镜像规范第 1 版本。

#### 通俗理解
1. 早期只有 Docker 自己的镜像格式，兼容性差；
2. 后来行业统一制定 OCI 标准，现在所有云厂商（腾讯 TCR、阿里云 ACR、Harbor、Docker Hub）存储的镜像默认都是 OCI 格式；
3. `OCI-Image-v1` = 标准通用容器镜像，Docker、K8s、nerdctl、containerd 全都能完美解析运行，没有任何兼容性问题。

#### 补充两种常见制品类型对照
- `OCI-Image-v1`：普通容器镜像（你当前前端 Nginx 镜像）
- `OCI-Index`：多架构镜像（同时包含 amd64+arm64，一个 Tag 自动适配不同 CPU）

### `docker compose up` 同时存在 `build` 和 `image` 两个字段时的规则

1. 优先执行本地构建镜像
2. 构建完成后，会给新构建出来的本地镜像打上 `image` 定义的标签
3. 最后再用这个标签启动容器

举个直观例子
```yaml
services:
  backend:
    image: ccr.ccs.tencentyun.com/xxx/backend:1.0.0
    build: ./backend
```

执行 `docker compose up -d` 完整流程：
1. 进入 `./backend` 目录，用 Dockerfile 本地 build 打包
2. 自动给刚打包好的镜像打上 tag：`ccr.ccs.tencentyun.com/xxx/backend:1.0.0`
3. 基于本地这个新镜像启动容器

### 关键坑点（对你现在场景非常重要）
1. 它不会去远程仓库 pull 镜像
哪怕远程 TCR 仓库已经存在 `1.0.0` 版本，compose 也会无视远程，自己在服务器本地重新构建一版，覆盖本地同名镜像标签。
2. 版本完全失控
服务器本地构建的镜像 ≠ 你本地推送到 TCR 的镜像，代码、产物不一致，极易出现线上 BUG。

### 两条命令行为差异
1. `docker compose up -d`
同时有 build + image → 本地构建，不走远程拉取

2. `docker compose pull backend`
只执行拉取操作时，只会读取 image 地址去拉远程镜像，不会触发 build 构建

### 最终给你的最佳实践
#### 1) 生产部部署文件（服务器用）
彻底删掉 `build:` 整行，只保留 `image`，保证永远远程 TCR 已发布镜像
```yaml
backend:
  image: ${TCR_REGISTRY}/${TCR_NAMESPACE}/github-monitor-backend:${BACKEND_TAG}
  # build: ./backend 删掉
```

#### 2) 本地开发调试文件（可以分开）
新建 `docker-compose.dev.yml`，本地开发用，只在自己电脑运行：
```yaml
# docker-compose.dev.yml 本地调试专用
backend:
  build: ./backend
  # image 可以注释掉
```

启动命令：
```bash
docker compose -f docker-compose.dev.yml up --build
```

一句话总结：
- 线上部署只留 image，删掉 build；本地调试单独配置带 build 的 compose 文件。
